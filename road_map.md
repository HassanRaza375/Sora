# Sora — Implementation Roadmap

Current state: foundation only. Build tooling, Tailwind v4 tokens, routing skeleton, and the Dexie schema are wired and verified. Every route renders `PlaceholderView.vue`. No feature UI, no shadcn-vue components generated, no stores/composables/services beyond scaffolding.

This roadmap sequences work so each phase only depends on what's already built — no phase requires jumping ahead.

---

## Phase 0 — Foundation (done)
- Vite + Vue 3 + TS build pipeline
- Dexie schema (`db.ts`, 10 tables) and models
- Tailwind v4 design tokens (type scale, radius scale, priority colors, light/dark theme)
- Routing skeleton with `meta` (title, icon, showInSidebar, showInBottomNav)
- shadcn-vue config (`components.json`, `cn()` util) — components not generated yet

## Phase 1 — Core plumbing (done)
Nothing else can be built cleanly until this exists.
- Hand-wrote the first batch of shadcn-vue primitives against the `new-york` / `neutral` config: `button`, `label`, `input`, `badge`, `checkbox`, `tabs`, `select`, `dialog`, `sheet` (the CLI still can't run on Node 20 — see CLAUDE.md)
- Built the shared `useLiveQuery` composable wrapping Dexie `liveQuery`
- Built `taskService` and `projectService` (Dexie access + business logic, framework-free)
- Built `useTasks` and `useProjects` composables on top of those services
- Built `Sidebar` (desktop, collapsible) and `BottomNav` (mobile) driven by `routes.ts` meta, wired together in a new `AppShell` and mounted from `App.vue`

Note: composables call services directly (no Pinia store in between) — `useLiveQuery` already gives every subscriber live, cross-tab-reactive data, so a Pinia domain store would just duplicate that. `stores/` stays reserved for transient UI state (drawer open/close, command palette, settings) whenever a later phase needs it.

## Phase 2 — Task creation drawer (done)
Almost every other view needs a way to create/edit tasks first.
- `useTaskDrawer` composable: `isOpen`/`taskId` are `computed` off `route.query.task` (not a separately-synced ref), so back-button/Escape/overlay-click all close it for free
- `TaskDrawer.vue` (Sheet-based): Task section (title, project select, priority select, status select, Today checkbox), Schedule section (due date, estimated duration, disabled recurrence placeholder), Details section (notes textarea, subtasks checklist with add/toggle/remove)
- New task: `openTaskDrawer()` with no id creates an empty-title draft via `taskService.createDraftTask()` immediately, then navigates to `?task=<id>` — create and edit share one autosave path
- Autosave: per-field debounced (~400ms) writes for title/notes/duration/due date; immediate writes for discrete fields (project, priority, status, Today) — no save button
- `taskService.listTasks()` filters out empty-title drafts so they don't leak into Inbox/Tasks/Today; `getTask(id)` is the unfiltered read the drawer itself uses
- New `useTask(taskId)` composable (live single task + its subtasks, keyed by a reactive id) and a `resubscribeOn` param added to `useLiveQuery` to support it
- New `Textarea` shadcn-vue primitive (wasn't in Phase 1's batch)
- "New Task" trigger added to `Sidebar` (button, top of nav) and `BottomNav` (raised FAB)
- Verified with `npm run build` plus an actual Playwright-driven browser session: open/fill every field/add-remove subtask/close via Escape/close via real browser back button/hard reload-persistence — zero console errors

**Follow-up fix (same day):** abandoned empty-title drafts are now cleaned up. Added `Task.createdViaDraft` (`boolean`, only ever set `true` by `createDraftTask()`, never cleared). `TaskDrawer.vue` watches `taskId` and, on any transition away from a task (close via any path, or switching tasks), deletes it if `createdViaDraft` is still `true` AND the local `title` ref is still empty — using the local ref rather than re-fetching from Dexie, since the title save is debounced and a fresh read could still see a stale empty title. Fixing this also surfaced a real bug: the debounced field saves were reading `taskId.value` (the drawer's *current* task) at fire time instead of capturing the target id at schedule time, so closing within the ~400ms debounce window could silently drop a pending save entirely — fixed by passing the id as an argument into each debounced function. Verified with `npm run build` plus a Playwright session against raw IndexedDB reads: (a) close without typing → row gone, (b) type a title, close normally → row persists with that title, (c) type a title, close *immediately* (before the debounce would've fired) → row still persists with the title, confirming the fix. See CLAUDE.md's Routing section for the full mechanism.

## Phase 8 — Planning system (done)

**Part A — Availability**
- New `availabilityService.ts` (framework-free): CRUD for `availabilitySchedules` (keyed by weekday, upserted — never seeded automatically) and `unavailablePeriods`, plus pure calc functions `defaultScheduleFor(weekday)` (Mon–Fri 9–5 fallback, Sat/Sun 0 min — computed only, never written), `isDateUnavailable()`, `capacityMinutesForDate(dateIso, schedules, periods)` (working hours minus breaks minus a full-day override from any overlapping unavailable period — `UnavailablePeriod` has no time-of-day fields, so it always blocks the whole date)
- New `useAvailability()` composable: thin reactive wrapper (`capacityFor(dateIso)`, `scheduleFor(weekday)`) over the same pure functions, mirroring the `summarizeWorkload`/`useWorkload` split from Phase 6
- New `PlanningView.vue` at `/planning` (not nested under `/settings` — Settings stays a placeholder until Phase 12, and nesting would've fought the existing "Settings tabs, not nested routes" decision). Not in Sidebar/BottomNav; reached via a new "Availability" link next to Plan My Day in `TodayView.vue`, or by URL. Weekly availability rows write straight through `upsertSchedule()` on change (no local draft state — `scheduleFor()` is itself reactive, so the display updates from the write-through); unavailable periods are a small explicit create/delete list, no confirm-before-delete (trivially undoable)
- New `src/utils/date.ts` addition: `weekdayOf(dateIso)` (local-safe weekday extraction, avoiding the same UTC-midnight-parsing bug class `localIso`/`todayIso` fix elsewhere); new `src/utils/duration.ts` addition: `parseTimeToMinutes(hhmm)`

**Part B — Planner**
- New `plannerService.ts` (framework-free): `buildRecommendation(candidates, capacityMinutes)` sorts by the spec's exact waterfall (priority → deadline → estimated duration, each level only breaking ties left by the one before it) then greedily packs the sorted list into capacity — not bin-packing, and deliberately keeps checking every task after one overflows, so a smaller lower-priority task can still land in the plan after a bigger higher-priority one didn't fit. An overloaded day is a valid result (more of the list lands in `overflowTaskIds`), never an error. `savePlan()` (full regeneration) is the only place `generatedAt` refreshes; `updatePlanItems()` (manual adjustment) leaves it untouched
- New `usePlanner()` composable: candidate set is `todayTasks ∪ overdueTasks` (deduped) per the spec's task-selection rule; scoped to today only (no date param — Plan My Day has no date picker). `generatePlan()` is a **no-op if today already has a `DailyPlan`** — Plan My Day is always safe to click repeatedly. `regeneratePlan()` is the one explicit path that replaces an existing plan, called only from a confirm dialog. `moveToOverflow`/`moveToPlanned`/`reorderPlanned` write straight through to the stored `DailyPlan`
- New `PlanPanel.vue` (`src/components/today/`): renders when a plan exists (self-contained, no duplicate guard needed in `TodayView.vue`), shows Planned/Overflow lists with priority badge + duration per task, a live capacity-vs-planned summary, up/down reorder buttons and move-to-other-section buttons (buttons, not drag-and-drop — reordering a short single list doesn't need DnD's complexity the way Kanban's cross-column drag did), and a "Regenerate" button behind a `Dialog` confirm (`ProjectDetailView`'s delete-confirm pattern) warning that it discards manual changes
- `TodayView.vue`: "Plan My Day" button is enabled (no longer disabled/tooltip-only), wired to `generatePlan()`; new "Availability" link to `/planning` added next to it
- Verified with `npm run build` plus two Playwright sessions: set today's weekday to a tight 60-minute window, created 4 candidate tasks (Urgent/30m, High/90m, Medium/20m, no-priority overdue/15m) and confirmed the exact expected split (Urgent Short + Medium Quick planned at 50m, High Long + the no-priority task in overflow) — this specifically exercised "a big task overflowing doesn't block a smaller one further down from still fitting"; confirmed re-clicking Plan My Day was a true no-op; manually moved a task from overflow to planned and reordered within planned, reloaded the page, and confirmed both survived (real persisted `DailyPlan` state, not local UI state); opened Regenerate, cancelled it (confirmed no change), then confirmed it (confirmed it reset to the original algorithm output, discarding the manual adjustments); separately verified availability persistence (custom hours surviving reload), adding a break, and a zero-capacity day via an `UnavailablePeriod` (both candidate tasks correctly landed in Overflow with a "0m available" summary — no error state). Zero console errors across both sessions.

## Phase 9 — Recurring tasks (done)
- Decided up front: recurring instances never auto-set `today: true` at generation — only `dueDate`. `today` stays a purely user-controlled toggle, same as a one-off task
- New `recurrenceService.ts` (framework-free): CRUD for `RecurringRule` (`listRules`/`getRule`/`createRuleForTask`/`updateRulePattern`/`setRuleActive`), `listInstancesForRule`, plus the pure `occurrencesInWindow(rule, windowStart, windowEnd)` covering all 7 spec frequency types (daily, weekly, weekdays, specificWeekdays, interval, monthly, yearly) and the idempotent `generateInstancesForRule(ruleId)` (diffs computed occurrence dates against existing `RecurringInstance.occurrenceDate`s for the rule, only creates what's missing)
- Generation window: rolling **30 days from "today"** at generation time, not from the rule's `startDate` and not unbounded — re-runs safely from multiple triggers since it's a pure diff-and-fill each time. `weekly`/`interval` step-anchor to `rule.startDate` (not the window) so the cadence never drifts between top-ups
- Both eager and lazy generation triggers, since one alone isn't enough for an offline-first PWA with no backend: **eager** — `createRuleForTask`/`updateRulePattern` call `generateInstancesForRule` immediately, so a new/edited rule fills its whole window on the spot; **lazy top-up** — `ensureWindowTopUp()` (filters `active` rules in JS, not a Dexie boolean `.where()` — see CLAUDE.md's IndexedDB boolean-key note) runs once from `App.vue`'s `onMounted`, so a rule catches back up to the current window the next time the app is opened, however long it's been. Deliberately does NOT backfill dates that are now in the past (e.g. after 2 weeks away) — recurrence only ever projects forward from "now", avoiding a backlog flood
- `TaskDrawer.vue`'s Recurrence section replaces the Phase 2 disabled stub: frequency picker + type-specific fields (interval count, weekday toggles, day-of-month, month), one context-sensitive action button ("Set recurrence" / "Update recurrence" / "Remove recurrence"), plus a one-click Pause/Resume. Creating anchors the rule to the task's own due date (defaulting to today, written back if it had none) and links the current task as the rule's first instance rather than duplicating it. Pausing/removing never deletes the rule or its instances — only stops future generation, per "history is preserved"
- `taskService.setTaskStatus()` now also syncs the linked `RecurringInstance.status` (`done` -> `'completed'`), so Phase 11's "recurring task completion" insight has real data to read
- `taskService.createTask`/`NewTaskInput` extended with `recurringRuleId`; new `src/utils/date.ts` export `parseLocalDate` (refactored out of `weekdayOf`) for recurrenceService's date-arithmetic reuse
- Verified with `npm run build` plus two Playwright sessions (the second using Playwright's `page.clock` API to simulate time passing, since this phase's core claims — "generates more over time," "doesn't duplicate," "stops when paused" — can't be verified any other way): a weekly rule generated exactly 5 correctly-spaced instances across the 30-day window; a same-day reload left the count unchanged (idempotent); a simulated +20-day jump + reload extended the window to 8 instances with zero duplicate dates and the weekday phase intact; pausing the rule then jumping +40 days total generated nothing further while every prior instance remained; a task's Inbox membership correctly updated (left Inbox) the moment recurrence auto-assigned it a due date; a generated instance correctly appeared on Calendar's day cell, in none of Today's three sections while due today (confirming the `today`-flag decision's real consequence), in Today's Overdue section once its due date passed, and as a Plan My Day candidate at that point. Zero console errors across both sessions.

## Phase 10 — Notifications & reminders (done)
- Decided up front: completing or deleting a task cancels its pending/snoozed reminder(s) — same cascade principle as `deleteTask()`'s existing subtask cleanup. `taskService.setTaskStatus(id, 'done')` soft-cancels (`status: 'dismissed'`) via a direct `db.reminders` lookup (same pattern as the Phase 9 `RecurringInstance` sync, no new cross-service import); `deleteTask()` hard-deletes reminders in the same transaction as subtasks
- New `reminderService.ts` (framework-free): CRUD (`listReminders`/`listActiveReminders`/`getReminderForTask`/`upsertReminderForTask`/`removeReminderForTask`/`markFired`/`snoozeReminder`) plus `computePresetTriggerAt(dueDate, dueTime, offset)`. Confirmed the `Reminder` model's `triggerAt` (an absolute ISO instant) already supports an arbitrary custom offset with no schema change — `offsetType: 'custom'` is just a label, the concrete trigger time is resolved once at creation either way
- One reminder per task (`upsertReminderForTask` finds-or-replaces in place), mirroring `recurrenceService`'s create/update split
- Presets require both a due date AND a due time on the task to compute a precise trigger instant — Phase 10 added the **Due time** field to `TaskDrawer.vue` (the `Task.dueTime` model field/service support already existed since early phases but was never exposed in the UI). Missing the time disables preset selection with an inline hint; `custom` (an explicit datetime-local picker) works regardless
- New `useReminderScheduler.ts`: a **30-second polling interval**, not a `setTimeout` per reminder at its exact future fire time — a backgrounded/suspended tab can have long `setTimeout`s throttled or paused by the browser, which would silently drop a reminder due to fire while inactive. Polling instead compares "now" against every pending/snoozed reminder's fire time each tick, so a throttled/skipped tick just delays a reminder, never silently loses it. Started once from `App.vue`'s `onMounted` alongside the Phase 9 recurrence top-up
- Notification permission requested only from the drawer's "Set/Update reminder" action (when `Notification.permission === 'default'`), never proactively on app load. A denied/unsupported `Notification` API never blocks task/reminder creation — the reminder still saves and still marks itself `'fired'` at its time, it just shows nothing visible
- **Actual vs. spec'd notification actions**: the `Notification` API's `actions` button array requires a service worker, which CLAUDE.md's existing architecture explicitly rules out — so only "Open task" is real on the notification itself (click → focus + `openTaskDrawer`). "Complete" is the drawer's existing Status control (already there); "Snooze 10 min" is a new button in the drawer's Reminder section, shown once a reminder has fired. This is a documented, deliberate scope reduction from the spec's literal wording, not a silent gap
- Verified with `npm run build` plus two Playwright sessions, using a fully-scripted `Notification` fake (`page.addInitScript`, permission state persisted via `localStorage` so it survives reloads like a real browser grant does) combined with `page.clock` to simulate time passing: a reminder fired exactly once at its trigger time after a fast-forward; a second task's reminder, completed before its trigger time, never fired (`dismissed`); a third task's reminder, deleted before its trigger time, was cascade-removed entirely (verified via `taskService.deleteTask()` called directly as a real ES module import, since there's no user-facing "Delete task" button yet); clicking the fired (fake) notification correctly opened the right task's drawer and closed the notification; and a full session with permission fixed at `'denied'` confirmed task/reminder creation succeeded, no `requestPermission()` re-prompt fired when already denied, and the reminder still transitioned to `'fired'` internally with zero visible notification and zero console errors.

## Phase 11 — Insights (done)
- **Found and fixed a real prerequisite gap**: `completionHistory` (table + doc comments since Phase 0) had never actually been written to by anything. `taskService.setTaskStatus()` now appends a `CompletionHistoryEntry` on every genuine todo/in_progress → done transition, snapshotting title/priority/estimatedDuration/projectId, plus `wasPlanned`/`planDate` (true only if the task is in *today's* `DailyPlan.items` at the moment of completion — never a historical plan)
- New `insightsService.ts` (`listCompletionHistory`, `listDailyPlans`) and a `recurrenceService.listAllInstances()` addition; both fetch full tables and let `useInsights.ts` filter client-side, consistent with the rest of the app's "small personal dataset, filter in JS" approach
- New `useInsights(range)` composable — range is `'week' | 'month' | 'all'`, rolling windows (last 7/30 days), not calendar-aligned boundaries, matching the rolling-window precedent already used elsewhere (Upcoming deadlines, recurrence generation)
- New `InsightsView.vue` at `/insights` (replacing `PlaceholderView`): a `?range=` URL-synced tab selector (`router.replace`, same "view toggle" convention as Tasks/Calendar, not Calendar's `?month=` navigation exception) driving every metric section from one shared state, plus stat cards for each spec'd metric — simple numbers/a reused `Progress` bar, no new chart components, per "light analytics, not a dashboard"
- **Metric definitions** (stated explicitly, since the spec doesn't define any of these precisely): tasks completed = `completionHistory` count in range (local-day-converted `completedAt`, not raw UTC comparison); completion rate = completed-in-range ÷ (completed-in-range + currently-open tasks); workload = `summarizeWorkload()` (Phase 6) over tasks due in range; project progress = `useProjectProgress()` (Phase 5) as-is, explicitly **not** range-filtered (always-current, stated in the UI); recurring completion = one combined N-of-M across all rules, `RecurringInstance.occurrenceDate` in range, deliberately capped at "today" so not-yet-due future instances never dilute the denominator; planning accuracy = (completions with `wasPlanned` + `planDate` in range) ÷ (sum of all `DailyPlan.items.length` for plans with `date` in range) — aggregated as one ratio across the range, not an average of daily percentages, so differently-sized plan days weight proportionally rather than equally
- Verified with `npm run build` plus two Playwright sessions: seeded a multi-day dataset via `page.clock` (completions 8/3/0 days back, due-dated tasks at 0/-2/-10 days, a 3-task plan run on a simulated day -2 with 2 of those completed same-day) and cross-checked **every displayed number against an independent recomputation from raw IndexedDB** (not the app's own code, a from-scratch reimplementation of each stated definition) across all three range tabs — exact match throughout, including the boundary cases (an 8-days-back completion correctly excluded from "week" but included in "month"/"all"; a 10-days-back due date the same way for workload). One seeding artifact (a workload-test task's due date had already gone overdue by the simulated plan day, correctly pulling it into that day's plan as a 4th candidate) grew the hand-predicted planning-accuracy denominator from 3 to 4 — the independent recomputation matched the UI's actual 4 regardless, which is exactly the point of recomputing from data instead of trusting a prediction. A second session verified recurring completion specifically: a daily rule started 10 days back generated 31 instances total, of which exactly 11 had `occurrenceDate <= today`; completing 4 of those showed "4 of 11 (36%)" in Insights, matching precisely. Project progress cross-checked identically between `/insights` and `/projects` for the same project. Zero console errors across both sessions.

## Phase 12 — Settings (done)
- **`/planning` absorbed into Settings' Planning tab** — the standalone route Phase 8 deliberately left undecided is gone; `PlanningView.vue`'s logic moved as-is into `src/components/settings/PlanningSettings.vue`, and `TodayView.vue`'s "Availability" link was removed (one path to the UI now, not two)
- New `SettingsView.vue` at `/settings` (replacing `PlaceholderView`): sections are `?tab=appearance|planning|notifications|data`-synced tabs within one view (not nested routes, per the existing architecture decision), each tab a self-contained component in `src/components/settings/`
- **Appearance**: new `useTheme.ts` — a module-level singleton `ref` (not a fresh ref per call), applied at import time so the `.dark` class lands on `<html>` as early as possible. All light/dark CSS tokens already existed in `tailwind.css` since Phase 0; this phase only built the toggle mechanism. "System" tracks `prefers-color-scheme` live via a `change` listener, verified in Playwright reacting to `page.emulateMedia()` with no reload needed
- **Notifications**: new `useNotificationsPreference.ts` (same module-singleton pattern, `localStorage`-backed, defaults on) — a master switch `useReminderScheduler.ts`'s `fire()` now checks alongside `Notification.permission`; off doesn't pause/delete reminders, just suppresses the visible `Notification`. Separately, `NotificationsSettings.vue` surfaces browser permission status and an "Enable" button that only appears when permission is `'default'` — re-requesting after an explicit `'denied'` doesn't re-prompt (browsers suppress that), so the UI says so directly instead of showing a button that can't do anything
- **Data**: new `dataService.ts` (framework-free) — `exportAllData()`/`clearAllData()`/`importAllData()` over one explicit `ALL_TABLES` list covering all 10 Dexie tables. Export doubles as "Backup" (same function, one button — no server in this architecture for a separate backup target to mean anything different). Import is a **destructive replace** inside one atomic transaction (clear then bulk-restore), not a merge — this schema's cross-table references (RecurringInstance/DailyPlan/Reminder all pointing at task ids) could easily dangle or duplicate under a naive merge. Clear Data wipes every table including `completionHistory` (a full reset, per the Phase 11 decision) — scoped deletes (`deleteTask()`) still leave `completionHistory` untouched, unchanged precedent
- **Real bug found via Playwright, not inspection**: the import file-picker held its parsed payload in a plain `ref()`, which Vue deep-wraps in a reactive Proxy — IndexedDB's structured clone can't serialize a Proxy, so every import silently failed with a `DataCloneError`. Fixed with `shallowRef`, matching `useLiveQuery.ts`'s own existing choice; documented in CLAUDE.md as a repeatable footgun for any future code reading a Dexie-shaped object out of reactive state before writing it back
- Verified with `npm run build` plus three Playwright sessions: theme cycling through System/Light/Dark including live OS-preference reactivity and persistence across reload; the notifications toggle firing zero visible notifications while off and exactly one once re-enabled (same reminder setup both times), permission-status display and the no-re-prompt-after-denial behavior; and a full seed → export → clear → verify-every-view-empty (Today/Inbox/Tasks/Projects/Calendar/Insights, not just a raw IndexedDB read) → import → verify-full-restoration cycle across all 10 tables, with Insights' `completionHistory`-derived "Tasks completed" number matching exactly before the clear and after the import. Zero console errors across all three sessions.

## Phase 13 — Search & command palette (done)
- New `useCommandPalette.ts` — a fourth module-level singleton (`isOpen`, `query`) alongside Phase 12's `useTheme`/`useNotificationsPreference`, with a global Ctrl/Cmd+K `keydown` listener attached once at module scope. Chose Ctrl+K/Cmd+K as the near-universal command-palette shortcut (VS Code, Linear, Notion, GitHub) since nothing in this codebase had already established a different convention
- **State decision**: `isOpen`/`query` are plain in-memory state, not URL-synced — a deliberate exception to the `?tab=`/`?range=`/`?view=` convention (Tasks/Calendar/Insights/Settings), since those represent bookmarkable "which mode of a persistent view" state while a transient overlay with no per-item deep-linking need (unlike the task drawer's `?task=`) has nothing worth putting in the URL
- **Search scope decision**: a live client-side filter over `useTasks()`/`useProjects()`'s existing reactive arrays (task titles + project names, case-insensitive substring), not a new indexed search structure — a personal task app's dataset is small enough to scan on every keystroke for free. Notes/subtasks not searched; done tasks still findable (unlike most list views)
- New `CommandPalette.vue` (`src/components/layout/`, mounted globally in `AppShell.vue`): one unified, always-filterable list across 4 possible sections (Tasks, Projects, Navigate, Actions) — Tasks/Projects only appear once a query is typed, Navigate/Actions show their full set by default and narrow as you type. - **Actions**: exactly "New Task" (`openTaskDrawer()`, reused) and "Plan My Day" — the latter reads `usePlanner().hasPlan` and relabels to "View today's plan" once today's already planned, navigating there instead of re-invoking the (already-safe-no-op) `generatePlan()`, so the palette never shows a button that would visibly do nothing. - Built on the existing `Dialog`/`DialogContent` primitives (reshaped via the `class` prop), not a new component family — this also front-loads most of the palette's accessibility groundwork instead of deferring it to Phase 14's app-wide pass: reka-ui's `DialogContent` already provides focus trapping, `role="dialog"`, Escape-to-close, and focus return, for free. Added `sr-only` `DialogTitle`/`DialogDescription` since the visual design has no visible heading. Keyboard nav (`ArrowUp`/`ArrowDown` wrapping through one flattened cross-section list, `Enter` to run) is the one piece the palette owns itself, bound via `@keydown` on the search input
- Two visible triggers: `Sidebar.vue` (a "Search" button with a ⌘K hint badge) and `BottomNav.vue` (a second small floating circle next to New Task, not a 6th flex-1 nav item) — the mobile trigger matters more in practice, since there's no keyboard shortcut path on a touch device
- Verified with `npm run build` plus two Playwright sessions: opened via the keyboard shortcut and via both visible triggers (including on a 400px mobile viewport); searched for a seeded task and opened its drawer; fully keyboard-only operation (type to filter, arrow keys, Enter, Escape) with zero mouse interaction; navigated to all 7 main views; triggered "New Task"; confirmed "Plan My Day" correctly relabeled to "View today's plan" after actually generating a plan through the palette; confirmed correct rendering in both light and dark theme via screenshots. Zero console errors across both sessions
