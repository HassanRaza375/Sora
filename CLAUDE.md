## Verification

`npm run build` (type-checking) is necessary but not sufficient for interactive or stateful UI behavior — autosave/debouncing, query-param sync, timers, drag/drop, anything with a time or event dimension the type checker can't exercise. When a phase involves any of that, also drive the actual app (a headless browser or equivalent) through the behavior in question, not just the build, and report what was checked and how in the session summary. Phases that are pure logic/plumbing with no runtime behavior to exercise (a service function, a Dexie schema change, a type-only refactor) can stay build-only.

## Architecture

One-directional data flow; do not skip layers:

```
Components → Composables → Services → Dexie (IndexedDB)
```

Composables call services directly — there is **no Pinia store in this data path**. `useLiveQuery` (wrapping Dexie's `liveQuery`) already gives every subscriber live, cross-tab-reactive data, so inserting a Pinia store between composables and services would just duplicate that reactivity for no benefit. `src/stores/` is reserved for transient, non-Dexie UI state (drawer open/close, command palette, settings) — populate it only when a phase actually needs shared UI state, not preemptively.

- **`src/components/**`** — presentational only. Domain components (`task/`, `project/`, `calendar/`, `today/`, `insights/`, `inbox/`, `settings/`) must not import services or `db` directly — they read from composables. `src/components/ui/` holds hand-written shadcn-vue primitives (see below); `src/components/layout/` holds `AppShell`/`Sidebar`/`BottomNav`; `src/components/task/` holds `TaskDrawer.vue` (mounted once globally from `AppShell.vue` rather than per-view, see Routing below), `TaskListItem.vue` (flat-row layout — Inbox, Tasks List view) and `TaskCard.vue` (Kanban's stacked-card layout, draggable). **They're deliberately two components, not one with a `variant` prop:** a single-line row and a stacked draggable card diverge enough in markup (and `TaskCard` alone needs `draggable`/`dragstart` wiring) that forcing them into one component would've meant more conditional branches than shared lines. They share `PriorityBadge` and the project-color-dot chip markup, and both call `useTasks()`/`useTaskDrawer()` directly for the status-toggle checkbox and click-to-open-drawer behavior rather than going through a wrapper composable — that behavior is ~3 lines, and this codebase's convention is already "components call composables directly," so wrapping it once more for two call sites wasn't worth it. If a third task-row layout shows up needing the exact same ~3 lines, *that's* the point to extract a composable, not before. `src/components/shared/PriorityBadge.vue` maps a `Priority` to one of the `--color-priority-*` tokens using a static `Record<Priority, string>` of literal Tailwind classes — Tailwind's scanner can't see a dynamically-built class string like `` `bg-priority-${priority}` ``, so that pattern silently produces no CSS. **Project colors are different:** a project's `color` is a free-form user-set string (hex), not a fixed enum, so there's no lookup table to build — `TaskListItem`/`TaskCard`'s project chip sets it via inline `:style="{ backgroundColor: project.color }"` instead. Don't reach for the enum-lookup pattern for per-instance user data; it only fits a fixed, known set of values like `Priority`.
- `src/components/project/` holds `ProjectDialog.vue` (create/edit) and `projectIcons.ts`. **`ProjectDialog` is a centered `Dialog`, not a `Sheet` like `TaskDrawer`, and uses an explicit Create/Save button, not autosave** — deliberately different from the task drawer: a project has 4 simple, rarely-revisited fields, not the kind of long-lived editing surface a task is, so replicating the drawer's debounced-autosave machinery would've been overhead for no real benefit. It's mounted locally per-view (`ProjectsView.vue` for create, `ProjectDetailView.vue` for edit) rather than globally like `TaskDrawer` — projects are only ever created/edited from those two specific places, not deep-linked into from everywhere the way tasks are, so there's no cross-view "open project X" need to justify URL-synced global state. **Icon** is a small fixed set (`projectIconKeys` in `projectIcons.ts`, ~10 lucide icons) rendered as a button grid, not a full icon picker — an MVP-appropriate tradeoff given `@lucide/vue` was already a dependency for nav icons; the map key (not the component) is what's persisted on `Project.icon`, so don't rename a key once real projects might be using it. **Color** is a fixed palette of 10 preset hex swatches in `ProjectDialog.vue`, not a native `<input type="color">` — an unconstrained picker could produce colors that clash with the calm/warm-neutral design system, so the UI curates a set that all work, while `Project.color` itself stays the free-form hex string the model already supported (nothing in `projectService`/`db.ts` needed to change for this). `src/composables/useProjectProgress.ts` derives `{ total, completed, percent }` per project from `useTasks().tasks` (a single-pass `computed` producing a `Record<projectId, ProjectProgress>`, plus a `progressFor(id)` convenience getter) — progress is never stored on the `Project` record itself, so it can't drift out of sync with the tasks. `src/components/ui/progress/` (`Progress.vue`) is a new shadcn-vue primitive, first used here.
- **`src/composables/**`** — feature-level logic (e.g. `useTasks`, `useTask`, `useProjects`, `useProjectProgress`, `useWorkload`, `useTaskDrawer`, `useAvailability`, `usePlanner`, `useRecurrence`/`useRecurringRule`, `useReminders`/`useReminderForTask`, `useReminderScheduler`, `useInsights`, `useTheme`, `useNotificationsPreference`, `useCommandPalette`) built directly on services, using `useLiveQuery` for reactive reads and plain async calls for mutations. `useWorkload.ts` is the odd one out — it doesn't touch Dexie/`useLiveQuery` at all, it's a `computed` wrapper around the pure `summarizeWorkload(tasks: Task[])` (count + summed `estimatedDuration`). Call `summarizeWorkload()` directly for a one-off array (e.g. Insights summarizing an arbitrary slice); use the `useWorkload()` composable when you want a reactive summary that tracks a reactive task list (as `TodayView.vue` does with `todayTasks`, and `useInsights()` does with tasks due in a range). `useTheme.ts`/`useNotificationsPreference.ts`/`useCommandPalette.ts` are a third case — no Dexie involvement at all (the first two are `localStorage`-backed; `useCommandPalette` is pure transient UI state), all three deliberately module-level singletons rather than the usual per-call composable shape, so every caller shares one state instead of each mount site getting its own out-of-sync copy.
- **`src/composables/useLiveQuery.ts`** — bridges a Dexie `liveQuery` to a Vue `shallowRef`, unsubscribing via `onScopeDispose`. Every reactive read from Dexie should go through this rather than one-off `.toArray()` calls. Takes an optional third `resubscribeOn` argument (a `WatchSource`) for queries keyed by a reactive value that isn't itself a Dexie table — e.g. `useTask(taskId)` re-subscribes whenever `taskId` changes, since Dexie's own change-tracking only re-runs the querier when a table it touched is written, not when an external ref changes. **Uses `shallowRef`, not `ref`, deliberately** — see the Settings section below for the real bug this exact distinction prevents (a plain `ref()` holding a Dexie-bound object deep-wraps it in a reactive Proxy, which IndexedDB's structured-clone algorithm can't serialize).
- **`src/services/**`** — Dexie table access + business logic that isn't view-specific (e.g. `taskService.ts`, `projectService.ts`, `availabilityService.ts`, `plannerService.ts`, `recurrenceService.ts`, `reminderService.ts`, `insightsService.ts`, `dataService.ts`). Services must stay framework-free (no Vue/Pinia imports) so the planner and recurrence algorithms can be unit tested in isolation. `db.ts` is the only place the `SoraDB` Dexie class is defined. Services return plain data and expose both query functions (for `useLiveQuery`) and mutation functions (create/update/delete) — they don't generate IDs or timestamps inconsistently, always via `src/utils/id.ts`'s `createId()` and `new Date().toISOString()`.
- **`src/models/**`** — plain TypeScript interfaces/types, re-exported from `src/models/index.ts`. These are Dexie's source of truth for table typing — update a model here before touching `db.ts`'s `.stores()` call.

### Data layer specifics

`src/services/db.ts` defines a single `SoraDB` (Dexie v1) with 10 tables: `tasks`, `subtasks`, `projects`, `recurringRules`, `recurringInstances`, `dailyPlans`, `availabilitySchedules`, `unavailablePeriods`, `completionHistory`, `reminders`. Notable non-UUID primary keys: `dailyPlans` is keyed by `date` (YYYY-MM-DD), `availabilitySchedules` by `weekday` (0–6). Schema changes must go through a new `this.version(n)` block, never editing version 1 in place.

**Never `.where(<boolean field>).equals(...)`.** `tasks`'s `today` and `recurringRules`'s `active` are both listed in `.stores()` as indexed boolean columns, but IndexedDB's key spec doesn't accept a plain boolean as a valid index key — a boolean-keyed `.where().equals()` lookup can't be relied on to match. Every boolean filter in this codebase is therefore done in JS over an already-fetched/live-queried array instead (`useTasks()`'s `todayTasks` computed; `recurrenceService.ensureWindowTopUp()`'s `rules.filter((r) => r.active)`), never as a Dexie `.where()` clause. The schema entries aren't wrong to have (Dexie ignores what it can't index), just don't reach for them.

`localStorage` is reserved for UI-only preferences (theme, sidebar collapsed, last view, notification toggle, default reminder offset) — everything else (all task/project/planning data) belongs in Dexie. This split is a deliberate product constraint, not an implementation detail — see the spec's Data Architecture section.

`completionHistory` is an append-only log that snapshots task fields (`title`, `priority`, `estimatedDuration`, `projectId`) at completion time rather than joining live task data, so Insights stay accurate after a task is edited or deleted later.

`taskService.listTasks()` filters out any task whose `title` is empty/whitespace — this is how empty-title drafts (see Routing below) stay invisible to every list view (Inbox, Tasks, Today, ...) without each one re-implementing the filter. `taskService.getTask(id)` is the unfiltered single-row read the drawer uses instead, and `taskService.createDraftTask()` is the one place an empty-title row gets created (and the only place `Task.createdViaDraft` is set `true` — every other creation path defaults it `false`). If you add another list query anywhere, route it through `listTasks()` (or replicate its filter) rather than querying `db.tasks` raw, or drafts will leak into it.

`useTasks()` already derives `inboxTasks` (no `projectId`, no `dueDate`, and `status !== 'done'`) and `inboxCount` (`inboxTasks.value.length`) as computeds over the one live `tasks` query — a view or nav component that needs the Inbox list or its count should consume these directly rather than deriving its own filter/count, so there's exactly one place the Inbox membership rule lives.

`useTasks()` also exposes single-criterion filter helpers matching `byStatus`/`byProject`'s shape: `byPriority(priority)`, `dueBetween(startIso, endIso)` (inclusive, plain string comparison since dates are `YYYY-MM-DD`), and `withoutDueDate()`. `TasksView.vue` doesn't chain these for its combined project+priority+due-date filter, though — chaining would allocate an intermediate array per criterion, so it writes one single-pass predicate instead that checks the same conditions inline. The exported helpers exist for a single-criterion caller to reuse rather than re-deriving the same logic — `TodayView.vue`'s "Upcoming deadlines" section is exactly that: `dueBetween(dateOffsetIso(1), dateOffsetIso(6))`, further filtered to `status !== 'done'` by the caller since `dueBetween` itself has no status opinion. Note `dueBetween` doesn't exclude `done` tasks on its own — every caller composes that explicitly (same as `TasksView.vue` does), so don't assume it's baked in.

`todayTasks` (`task.today && status !== 'done'`) and `overdueTasks` (`dueDate < today && status !== 'done'`) predate this phase (Phase 1) but Phase 6's `TodayView.vue` is the first thing to actually render them. They're independent of each other and of "Upcoming deadlines" — a task can in principle satisfy more than one (e.g. marked Today *and* due in 3 days) and would then appear in more than one section; this isn't specially prevented, since doing so would need each section to know about the others' membership for a scenario that's unlikely in normal use.

**`CalendarView.vue`** (Phase 7) is a single view file, not split into `src/components/calendar/` subcomponents — the month grid and agenda list are each simple enough (one `v-for` over a computed array) that extracting `CalendarDayCell`/`CalendarAgendaGroup` components would've been indirection without reuse; if Insights (Phase 11) or the planner (Phase 8) ever need the same grid, that's the point to extract it, not before. It reuses `dueBetween()` (pointed at `monthStartIso(visibleMonth)`/`monthEndIso(visibleMonth)` instead of Today's rolling 6-day window) and the `projectsById`/`projectFor()` lookup pattern from `TasksView`/`ProjectDetailView`/`TodayView`, filtering out `status === 'done'` the same way Today's "Upcoming deadlines" does. Month view renders each task as a small button (project-color dot + truncated title, no `TaskListItem`/`TaskCard` reuse — there isn't room for a full row in a day cell), capped at 3 per cell with a "+N more" label past that (no expand-on-click; the label alone satisfies "don't silently clip or grow unboundedly"). Agenda view has more room, so it reuses `TaskListItem` directly, grouped into date sections sorted chronologically by `dueDate` (then `dueTime`) — ordering *within* a day (among same-day tasks) is whatever `dueBetween()`'s underlying Dexie iteration order happens to be (effectively UUID order, not creation order), which is fine since the spec only calls for chronological grouping, not a same-day tiebreaker. Both views click through to the task drawer via the existing `openTaskDrawer(id)` — no new interaction pattern.

### Planning system (Phase 8)

**Availability.** `availabilitySchedules` (keyed by `weekday`, 0–6) only ever gets a row once the user actually edits that weekday in `PlanningView.vue` — nothing is seeded into Dexie on first load. A weekday with no row falls back to `availabilityService.defaultScheduleFor(weekday)` (Mon–Fri 9:00–17:00, no breaks; Sat/Sun 0 minutes), which is a **pure computed fallback, never written**. This is why Plan My Day produces something reasonable before Settings/Planning is ever touched, without silently writing data the user didn't ask to save — the Planning UI itself shows the same fallback pre-filled (so it looks configured) until the user's first edit actually persists a row. `UnavailablePeriod` blocks the **entire** date range it spans (capacity 0 for any date `startDate <= date <= endDate`) — the model has no time-of-day fields, so there's no way to represent a partial-day block; `allDay` exists on the model but isn't read by `capacityMinutesForDate()`, since every period is effectively all-day given the current fields. `capacityMinutesForDate(dateIso, schedules, periods)` (working hours minus breaks minus a full unavailable-day override) is a pure function in `availabilityService.ts`, not the composable — `useAvailability()` is a thin reactive wrapper (`capacityFor(dateIso)`) so `plannerService`/anything else framework-free can call the same math directly with already-fetched arrays, mirroring the `summarizeWorkload`/`useWorkload` split from Phase 6.

**`PlanningSettings.vue`** (`src/components/settings/`, rendered from Settings' Planning tab — see the Settings section below for the Phase 12 move from its original standalone `/planning` route) is the availability UI. Each weekday row writes directly through `upsertSchedule()` on `@update:model-value` (no local draft state, no debounce) — since `scheduleFor(weekday)` is itself reactive (it reads the live `schedules` array with a pure-fallback default), the inputs' displayed value updates automatically from the write-through, the same "everything reactive from Dexie, no local mirror" approach as the rest of the app. Unavailable periods are a small, explicit create/delete list (closer to `ProjectDialog`'s pattern than the task drawer's autosave — a new period is a distinct entity being added, not a continuously-edited field), with no confirm-before-delete (removing a date-range block is trivially undoable by re-adding it, unlike deleting a project).

**`plannerService.ts`** (framework-free). `buildRecommendation(candidates, capacityMinutes)` sorts by the spec's exact waterfall — priority → deadline → estimated duration, each level only breaking ties left by the one before it (`PRIORITY_RANK`; no-priority and no-deadline both sort last via explicit sentinels) — then greedily walks the sorted list, appending each task to `items` if it still fits in the remaining capacity, otherwise to `overflowTaskIds`. **This is not bin-packing**: the loop doesn't skip ahead or backtrack to fit a smaller task before a bigger one that's next in priority order, and it deliberately keeps checking every task *after* one that overflowed (so a big high-priority task overflowing doesn't stop a smaller lower-priority one further down from still fitting) — verified in Playwright with a case where a 90-minute High task overflows a 60-minute capacity but a 20-minute Medium task after it still lands in `items`. An overloaded day (candidates exceed capacity) is a valid, non-error result — more of the sorted list just ends up in `overflowTaskIds`. `savePlan()` (full regeneration) is the only place `DailyPlan.generatedAt` is refreshed; `updatePlanItems()` (manual adjustment) intentionally leaves it untouched, since the algorithm didn't re-run.

**Never-silently-reschedules, concretely.** `usePlanner().generatePlan()` (what the enabled "Plan My Day" button calls) is a **no-op if a `DailyPlan` already exists for today** — clicking it repeatedly is always safe. The only path that replaces an existing plan is `regeneratePlan()`, called exclusively from `PlanPanel.vue`'s "Regenerate" button behind a `Dialog` confirm ("This discards any manual changes...") — modeled on `ProjectDetailView`'s delete-confirm pattern. This was a deliberate choice over "regenerate and ask" inline: making the primary button itself idempotent means there's no accidental-overwrite path at all, not even one behind a dialog a user might click through on the same button they use daily. Manual adjustment (`moveToOverflow`/`moveToPlanned`/`reorderPlanned` in `usePlanner.ts`) writes straight through `plannerService.updatePlanItems()` to the stored `DailyPlan` — verified surviving a full page reload in Playwright, confirming it's real persisted state, not local component state.

**`PlanPanel.vue`** (`src/components/today/`) renders only when `usePlanner().plan` exists (self-contained `v-if`, so `TodayView.vue` doesn't need its own duplicate guard before rendering it). Reordering planned tasks uses explicit up/down icon buttons per row, not drag-and-drop — unlike Kanban's column-to-column drag (justified there because dragging a card between columns *is* the natural gesture), reordering within a single short list is just as discoverable via buttons, much simpler to implement/verify (no `dataTransfer` wiring, trivially scriptable in Playwright), and this phase's list lengths don't call for DnD's added complexity. If a future phase needs cross-list drag for a longer plan, that's a reason to revisit, not a default.

### Recurring tasks (Phase 9)

**A generated instance is just a `Task`.** `recurrenceService.generateInstancesForRule()` creates an ordinary row via `taskService.createTask()` (with `recurringRuleId` set and `dueDate` set to the occurrence date) plus a `RecurringInstance` linking row — nothing about Today/Inbox/Tasks/Calendar/`usePlanner()` needed to change, since all of them already just read live `Task` rows with no awareness of where a task came from. This was true by construction, not by coincidence: the whole point of keeping generation confined to "write a normal Task row" was to avoid a second, parallel code path for recurring vs. one-off tasks anywhere else in the app — confirmed in Playwright by a generated instance correctly appearing in Calendar's day cell, Today's Overdue section once its due date passed, and as a Plan My Day candidate at that point, all with zero recurrence-specific code in those views.

**`today` is never auto-set on generation** (the flagged Phase 8 question, resolved before starting this phase) — only `dueDate`. `Task.today` stays a purely user-controlled toggle, identical for a generated instance and a one-off task; nothing makes assumptions about a recurring task being more "urgent" than any other. One concrete, verified consequence: a daily rule's instance due *today* shows in none of Today's three sections (not "Today's tasks" — not `today`-flagged; not "Overdue" — not yet overdue; not "Upcoming" — due today isn't upcoming) until either the user manually toggles Today on it, or its due date passes and it becomes Overdue. This is working as intended, not a gap — don't "fix" it by auto-flagging `today` later without an explicit decision to reverse this one.

**Generation window: rolling 30 days from "today" at generation time**, not from the rule's `startDate` and not unbounded — an indefinite `daily` rule would otherwise generate forever. `recurrenceService.occurrencesInWindow(rule, windowStart, windowEnd)` is a pure function computing which dates in `[windowStart, windowEnd]` (clamped to the rule's own `[startDate, endDate]`) match the pattern; `generateInstancesForRule(ruleId)` calls it with `[todayIso(), dateOffsetIso(30)]`. **`weekly`/`interval` step forward from `rule.startDate`, not from `windowStart`** — anchoring the phase to the rule's actual start date so the cadence (which weekday, which day of an N-day cycle) never drifts between repeated top-up calls with different windows; `daily`/`weekdays`/`specificWeekdays` don't have a phase to preserve, so they scan the clamped window directly for efficiency. Verified in Playwright: a weekly rule kept landing on the same weekday after a simulated 20-day jump extended the window.

**Idempotent by construction, not by a duplicate-check flag.** `generateInstancesForRule()` always recomputes the full set of in-window occurrence dates, diffs it against existing `RecurringInstance.occurrenceDate`s for that rule (`db.recurringInstances.where('ruleId').equals(ruleId)`, filtered in JS — see the boolean-index note above for why this couldn't use a compound `[ruleId+occurrenceDate]` index either without a schema version bump, which wasn't worth it for this data volume), and only creates rows for dates not already present. This makes it safe to call from multiple triggers without any of them needing to know about the others: **eager** generation right after `createRuleForTask()`/`updateRulePattern()` (fills the whole window immediately so the rule feels "real" the moment it's created, not after the next reload) and **lazy top-up** via `ensureWindowTopUp()`, called once from `App.vue`'s `onMounted`. The lazy path is necessary regardless of the eager one: this is an offline-first PWA with no backend, so nothing generates future instances while the app isn't open — if it's not opened for two weeks, only a check-on-load can catch the window back up, since there's nothing to run a server-side cron. Verified in Playwright: same-day reload leaves the instance count unchanged; a simulated 20-day-forward reload (via Playwright's `page.clock`) extends the window with new instances and zero duplicates; pausing the rule then jumping forward further generates nothing new while leaving every previously-generated instance and its history untouched.

**Deliberately does not backfill missed past dates.** Because the window is always `[today, today+30]`, a date that's now in the past is never generated even if the app was closed straight through it — e.g. reopening after two weeks away doesn't retroactively create 14 now-overdue instances of a daily task. Recurrence only ever projects forward from "now"; this is a product decision (avoiding a backlog flood nobody asked for), not a missed edge case.

**Creating/editing recurrence from the task drawer** (`TaskDrawer.vue`'s Recurrence section, replacing the Phase 2 disabled stub) is scoped deliberately narrow: a frequency `Select` (the 7 spec types plus "Does not repeat") with type-specific fields (interval count, a weekday toggle row, day-of-month, month), backed by one context-sensitive action button — **"Set recurrence"** (no rule yet) creates one via `createRuleForTask(taskId, pattern)`, which anchors `RecurringRule.startDate` to the task's own `dueDate` (defaulting to today and writing it back to the task if it had none — synced into the drawer's local `dueDate` ref immediately so the field doesn't look stale until reopened) and links the *current* task as the rule's first instance rather than creating a duplicate. **"Update recurrence"** (rule exists, a frequency is still selected) patches the pattern fields and re-snapshots `taskTemplate` from the task's current fields via `updateRulePattern()`, then re-runs generation — additively; it never touches or deletes instances already generated under the old pattern. **"Remove recurrence"** (rule exists, "Does not repeat" selected) and the separate one-click **Pause/Resume** control both do the same thing — `setRuleActive(ruleId, false/true)` — never delete the rule or its instances, per "history is preserved." There's no UI yet for editing a rule's `endDate` or for a dedicated recurrence-management view listing all rules — out of scope for this minimal pass; a future phase can add either without changing the underlying service functions.

**`taskService.setTaskStatus()`** now also syncs the linked `RecurringInstance.status` (`done` → `'completed'`, anything else → `'pending'`) when the task has one, via a direct `db.recurringInstances` lookup rather than importing `recurrenceService` — so a future Insights "recurring task completion" metric (Phase 11) reads real per-instance completion data instead of every instance being frozen at `'pending'` forever.

### Notifications & reminders (Phase 10)

**`Reminder.triggerAt` (an absolute ISO instant) was already sufficient for a "custom arbitrary offset" — no model change needed.** Every offset type, preset or `'custom'`, resolves to one concrete `triggerAt` at creation time; `offsetType` is just a label for what produced it (`reminderService.computePresetTriggerAt(dueDate, dueTime, offset)` for the 6 presets, or the custom datetime-local input's value converted straight to an ISO string). `new Date(`${dueDate}T${dueTime}`)` (a full date-*time* string) parses as **local** time per the `Date` constructor's own spec — unlike the date-only strings `date.ts` has to work around elsewhere, so no UTC bug here.

**Presets require both a due date AND a due time on the task** — "5 minutes before" is meaningless without knowing what time the task is due. Phase 10 added the **Due time** field to `TaskDrawer.vue` (`Task.dueTime` existed on the model/in `taskService` since early phases but was never exposed in the UI until now) specifically to make presets usable. If a task has a due date but no due time, the preset options are still selectable but the action button is disabled with an inline caption ("Set a due date and time to use this reminder option.") rather than silently no-op'ing — only `'custom'` (an explicit absolute date+time, independent of the task's own due date) works without one.

**One reminder per task, not a list** — `reminderService.upsertReminderForTask(taskId, pattern, dueDate, dueTime)` finds-or-replaces the task's single existing `Reminder` row (same id, fields updated) rather than accumulating multiple. `TaskDrawer.vue`'s Reminder section mirrors the Recurrence section's exact pattern one level down: a `Select` + type-specific input (the custom datetime picker), one context-sensitive action button (Set/Update/Remove reminder), reusing the same "no `initialized` gate needed, nothing writes until the button click" reasoning.

**Editing due date/time after a reminder is set does NOT auto-recompute it** — same "frozen at creation, no auto-reconciliation on edit" decision already made for `RecurringRule.taskTemplate` (Phase 9) and `RecurringInstance.occurrenceDate`. The reminder's status caption always shows its actual stored trigger time, so a stale reminder is visible, not silently wrong; clicking "Update reminder" again resyncs it from the task's current due date/time.

**Cascading cancellation lives in `taskService.ts`, not a new service dependency** (per the explicit Phase 10 instruction): `setTaskStatus(id, 'done')` soft-cancels (`status: 'dismissed'`) any `pending`/`snoozed` reminder for the task via a direct `db.reminders` lookup — the same "direct narrow lookup in the relevant table" pattern already used for the `RecurringInstance` sync right above it, not a `reminderService` import. Un-completing a task does **not** un-dismiss a cancelled reminder. `deleteTask()` **hard**-deletes the task's reminders in the same transaction as its subtasks — unlike completion's soft-cancel, there's no task left for a "dismissed" record to be about, and an orphaned pending reminder would otherwise keep matching in the scheduler forever for a task that no longer exists.

**`useReminderScheduler.ts`: a 30-second polling interval, not a `setTimeout` per reminder scheduled for its exact future fire time.** A backgrounded/suspended browser tab can have long `setTimeout`s throttled or paused outright, which would silently drop a reminder due to fire while the tab was inactive. Polling instead just compares "now" against every pending/snoozed reminder's fire time on each tick (`reminder.snoozedUntil` in place of `triggerAt` when snoozed) — if a tick itself gets throttled and skipped, the next one that does run still catches anything now overdue, so a reminder is delayed at worst, never silently lost. 30s is granular enough that no one perceives a reminder as late. Started once from `App.vue`'s `onMounted`, alongside `ensureWindowTopUp()` — foreground-only, per the pre-existing "no service-worker push" constraint this phase didn't change.

**Notification permission is requested from the "Set/Update reminder" action in `TaskDrawer.vue`, never proactively** — `Notification.requestPermission()` only fires when `Notification.permission === 'default'` (never yet asked), right before a reminder is actually about to be saved. The scheduler itself never prompts; at fire time it just checks `Notification.permission === 'granted'` and skips the visible `Notification` if not (the reminder is still marked `'fired'` internally either way, so it stops matching on future ticks). A denied/unsupported `Notification` API never blocks or errors task/reminder creation — verified in Playwright with permission fixed at `'denied'`: the task and reminder both save normally, nothing throws, and no notification appears once its time passes.

**Actual notification actions vs. the spec's list — "Open task" is the only one implemented on the notification itself.** The spec lists Open task / Complete / Snooze as notification actions, but the `Notification` API's `actions` button array (and any `notificationclick` handling of which button was pressed) **requires a persistent notification shown via a `ServiceWorkerRegistration`** — a plain page-constructed `new Notification(...)` (which is what foreground-only, no-push architecture requires per CLAUDE.md's existing PWA constraint) only supports a single `onclick` handler, no `actions` array. So: clicking the notification calls `window.focus()` + `openTaskDrawer(reminder.taskId)` (bringing the task up in the already-open app) — that's "Open task". **Complete** happens from the drawer's existing Status control once it's open (already there, nothing new needed — and per the cascade above, completing a task auto-cancels its reminder as a side effect). **Snooze** is a "Snooze 10 min" button in the drawer's Reminder section, shown once a reminder's status is `fired`/`snoozed` (`reminderService.snoozeReminder(id, minutes)` sets `status: 'snoozed'` + `snoozedUntil`). This is a real, documented scope reduction from the spec's literal wording, not a silent gap — if real actionable notification buttons are wanted later, that requires deciding to add a service worker, which is an explicit architecture change, not an incremental addition to this phase.

### Insights (Phase 11)

**`completionHistory` had never been written to before this phase — a real prerequisite gap, not something to work around.** The table and its doc comments existed since Phase 0 ("Snapshot of the task at completion time, so edits/deletes later don't skew history") but no service ever called `db.completionHistory.add()`. Since every completion-based Insights metric is specified to read from `completionHistory` rather than a live `status === 'done'` count (exactly so it survives later edits/deletes), Insights would have had zero data forever without this. `taskService.setTaskStatus()` now appends one `CompletionHistoryEntry` per genuine `todo`/`in_progress` → `done` transition (guarded against double-logging an already-done task), snapshotting `title`/`priority`/`estimatedDuration`/`projectId` at that instant. It also resolves `wasPlanned`/`planDate`: `true` + today's date only if this exact task is in *today's* `DailyPlan.items` at the moment of completion — completing a planned task a day late is a real planning miss, not a data-entry nuance, so this deliberately only ever checks the current day's plan, never a historical one.

**Range selection: `?range=week|month|all` in the URL, `router.replace`, one shared state for every metric section** — the same "view toggle" convention as Tasks' List/Kanban and Calendar's Month/Agenda (a small fixed set of options, switching between them shouldn't pile up back-button history), not Calendar's separate `?month=` exception (that one's about continuous navigation through a specific value, which range selection isn't). Defaults to `week` with the param omitted, matching Calendar's "the URL with nothing extra means the sensible default" pattern. `week`/`month` are **rolling windows** (last 7 / last 30 days including today), not calendar-week/month boundaries — consistent with the rolling-window precedent already used elsewhere (Today's "Upcoming deadlines" rolling 6 days, recurrence generation's rolling 30 days) rather than introducing calendar-aligned start-of-week/month math nothing else in the app needed. `all` uses an early sentinel date as the lower bound so `useInsights.ts`'s `inRange()` stays one lexical comparison for every range, no separate unbounded branch.

**Metric definitions actually built (the spec doesn't define these precisely either, so — same as Phase 8's planner waterfall — a concrete choice had to be made and stated):**
- **Tasks completed** = count of `completionHistory` entries with `completedAt` (converted to a local calendar day via `localIso()`, not compared as raw UTC strings — `completedAt` is a UTC `toISOString()` timestamp, so a naive string-range comparison against local day boundaries would have the same off-by-one risk `date.ts` works around elsewhere) falling in the range.
- **Completion rate** = completed-in-range ÷ (completed-in-range + tasks currently open). Reads as "of everything completed recently plus everything still on your plate, what fraction is done." Deliberately not tied to due dates — `completionHistory` has no due-date snapshot, so inventing due-date semantics for this one metric would mean supporting it from a different, inconsistent data source. "Currently open" isn't itself range-filtered (an open task has no "when" to filter by).
- **Workload** = `summarizeWorkload()` (Phase 6) applied to tasks whose `dueDate` falls in the range, instead of just `todayTasks`. Exactly the reuse instruction 1 called for, no new aggregation logic.
- **Project progress** = `useProjectProgress()` (Phase 5) rendered as-is, **not range-filtered** — it's already a live, all-time "current state of each project" number, and range-limiting it would answer a different question ("progress made in this window") that nothing asked for. The Insights section says so explicitly ("Always current — not affected by the range above.") so this isn't mistaken for a bug.
- **Recurring task completion** = one combined `N of M` across every `RecurringRule` (not a per-rule breakdown, since "light analytics" and a 7-type rule picker already exist elsewhere if someone wants per-rule detail), filtered by `RecurringInstance.occurrenceDate` falling in the range. Capping the range at "today" (never counting future-scheduled, not-yet-due instances) is deliberate, not a side effect of reusing `inRange()` — an instance that hasn't happened yet can't be "completed" or "missed", so including it would only dilute the denominator with instances that are neither.
- **Planning accuracy** = (`completionHistory` entries with `wasPlanned && planDate` in range) ÷ (sum of `DailyPlan.items.length` across every plan with `date` in range) — i.e. of everything ever recommended by a plan in this window, what fraction got done on the day it was planned for. Aggregated as one ratio across the whole range (sum of completed ÷ sum of planned), not an average of each day's percentage — averaging percentages would let a 1-of-1 day (100%) outweigh a 15-of-20 day (75%) just as much, which misrepresents a range with very differently-sized plans.

**Verification method: every displayed number was cross-checked against an independent recomputation straight from raw IndexedDB**, using the same definitions above re-implemented directly in the Playwright script (not by importing the app's own code) — this is a materially stronger check than "does the UI look internally consistent," since it validates the actual formulas against arbitrary seeded data across all three range tabs, not hand-picked round numbers. One seeded scenario surfaced a useful reminder rather than a bug: a task created for the "workload" test with a due date 10 days in the past had, by the time a `Plan My Day` was run on a simulated day 2 days ago, already become a legitimate `overdueTasks` candidate — so it correctly appeared in that day's plan alongside the 3 tasks the test meant to plan, growing the denominator from a hand-predicted 3 to the actual 4. The independent recomputation (built from real stored `DailyPlan` data, not the flawed manual prediction) matched the UI exactly regardless — a good example of why this phase's verification recomputes from data rather than trusting a pre-written expectation.

### Settings (Phase 12)

**`/planning` is gone — absorbed into Settings' Planning tab, per a decision Phase 8 deliberately deferred to this point.** `PlanningView.vue`'s logic/markup moved as-is into `src/components/settings/PlanningSettings.vue` (same `useAvailability()` composable, unchanged); the standalone route and `TodayView.vue`'s "Availability" link were both removed, so there's exactly one path to that UI now (Sidebar → Settings → Planning tab), not two.

**`/settings` sections are tabs within one view, not nested routes** (an architecture decision from early phases, finally exercised here) — `SettingsView.vue` is a thin shell: a `?tab=appearance|planning|notifications|data` URL-synced `Tabs` control (same `router.replace`/default-omitted-from-URL convention as Insights' range selector and Tasks' view toggle) that conditionally renders one of four presentational components in `src/components/settings/` (`AppearanceSettings.vue`, `PlanningSettings.vue`, `NotificationsSettings.vue`, `DataSettings.vue`). Each is self-contained and calls its own composable(s) directly, same convention as every other domain component in this codebase.

**Theme (`useTheme.ts`): a module-level singleton, not a per-call composable.** `theme` is a single `ref` created once at module-load time (not inside `useTheme()`), with its `localStorage` write, `<html>.dark` class toggle, and `prefers-color-scheme` change listener all attached once at that same module scope — every component that calls `useTheme()` shares the exact same state and side effects, rather than each call creating its own `localStorage`-backed ref that could drift out of sync with the others (there's no cross-instance sync mechanism for independent local refs writing to the same key). Applied at import time, not gated behind `onMounted`, so the class lands on `<html>` as early as the module graph reaches it — `App.vue` imports and calls it right at the top of `<script setup>` for exactly this reason. "System" re-applies live (verified in Playwright via `page.emulateMedia({ colorScheme })`) via the `prefers-color-scheme` media query's own `change` listener, no reload needed. All theme tokens (light + dark CSS variables) already existed in `tailwind.css` since Phase 0 — this phase only had to build the mechanism that actually toggles the `.dark` class; nothing about the visual design needed to change.

**Notifications tab — two genuinely different, independent axes**, both surfaced honestly rather than conflated into one toggle:
- **`useNotificationsPreference.ts`** (`notificationsEnabled`, `localStorage`-backed, same module-singleton pattern as `useTheme.ts`, defaults `true`) is an app-level "show visible notifications or not" master switch. `useReminderScheduler.ts`'s `fire()` now checks it alongside `Notification.permission === 'granted'` before constructing a `Notification` — turning it off doesn't pause or delete reminders, they still save, still mark themselves `'fired'` at the right time (so turning it back on doesn't cause a backlog to dump), they just don't pop up anything visible while it's off. Verified in Playwright: identical reminder setup fired zero visible notifications with the toggle off and exactly one with it back on.
- **Browser permission** (`Notification.permission`) is a separate, per-origin browser-level grant this app doesn't control. `NotificationsSettings.vue` shows the current status and offers an "Enable" button *only* when permission is `'default'` (never yet asked) — calling `Notification.requestPermission()` again after an explicit `'denied'` does **not** re-prompt; browsers deliberately suppress repeat prompts after a denial to prevent permission-prompt spam, and will just silently resolve to `'denied'` again. When status is `'denied'`, the UI says so directly and explains the only real fix is the browser's own site settings — it doesn't show a button that would appear to do something but can't.

**Data tab (`dataService.ts`, framework-free) — decisions made explicit, per the spec's underspecified wording:**
- **"Backup" and "Export" are the same feature, one button, not two.** There's no server in this architecture to back up to — a downloadable JSON snapshot of every table *is* the backup. Building a second, near-identical mechanism under a different label would've been pure duplication; `DataSettings.vue`'s copy says this outright rather than pretending they're different features.
- **`ALL_TABLES` in `dataService.ts` is one explicit array of all 10 Dexie tables**, referenced by `exportAllData`/`clearAllTables`/`importAllData` alike, specifically so a table added by a future phase has to be deliberately added to this one list (and will loudly fail type-checking on the destructured `exportAllData` result if forgotten) rather than silently missing from export/clear/import forever.
- **Import replaces, it does not merge.** `importAllData()` clears every table then `bulkAdd`s the file's contents, all inside one Dexie transaction (atomic — a failure partway through rolls back the whole thing, never leaving a half-imported mix of old and new data). A merge was considered and rejected: this schema has real cross-table references with no foreign-key enforcement (`RecurringInstance` → `RecurringRule`/`Task`, `DailyPlan` → task ids, `Reminder` → `Task`), and merging two independently-evolved datasets could easily produce dangling references or duplicated derived state with no clean resolution. Import is framed (in the UI copy and the confirm dialog) as "restore a backup / move to a new device," not "combine two histories."
- **Clear data wipes every table, `completionHistory` included** — a "reset" that quietly preserved analytics history wouldn't be a real reset, per the explicit Phase 11 decision this phase executes on. This is a **full-wipe-only** behavior distinct from scoped deletes: `taskService.deleteTask()` still never touches `completionHistory` (unchanged precedent from Phase 11) — only `dataService.clearAllData()`'s all-or-nothing wipe does. `localStorage` preferences (`theme`, `notificationsEnabled`) are untouched by Clear Data — they're device/UI preferences, not app data, per the same split CLAUDE.md's Data layer section already draws.
- **A real bug, found and fixed via Playwright, not by inspection:** the file-picker's parsed import payload was originally held in a plain `ref()`. Vue deep-wraps any object assigned into a `ref()` in a reactive `Proxy`; IndexedDB's structured-clone algorithm (which Dexie's `bulkAdd` relies on to actually write the rows) cannot clone a `Proxy`, so every import failed with a `DataCloneError` — silently from the UI's perspective, since the error was an unhandled promise rejection the confirm dialog didn't surface. Fixed by switching to `shallowRef` (which tracks reassignment but doesn't proxy-wrap the held value), matching `useLiveQuery.ts`'s own `shallowRef` choice exactly. **Any future code that reads a Dexie-shaped object out of a `ref()`/reactive state and feeds it back into a raw Dexie write should use `shallowRef` (or `markRaw`/`toRaw`) for the same reason** — this is a real, repeatable footgun in this architecture, not a one-off typo.

Every displayed table's emptiness/restoration after Clear/Import was verified by actually visiting Today, Inbox, Tasks, Projects, Calendar, and Insights (not just re-querying Dexie) — confirming every `useLiveQuery`-driven view reacts to a bulk `clear()`/`bulkAdd()` the same way it reacts to any other Dexie write, with no manual refetch or reload required anywhere in the app.

### Search & command palette (Phase 13)

**`useCommandPalette.ts`** is a fourth module-level singleton (`isOpen`, `query`, alongside Phase 12's `useTheme`/`useNotificationsPreference`) — its global Ctrl/Cmd+K `keydown` listener is attached once at module scope for the same reason those two attach their side effects once: every mount site (`Sidebar.vue`'s trigger, `BottomNav.vue`'s, `CommandPalette.vue` itself) shares one listener and one `isOpen` state instead of each wiring/tracking its own. **Ctrl+K / Cmd+K** was chosen as the near-universal command-palette convention (VS Code, Linear, Notion, GitHub, Superhuman) — nothing already in this codebase had established a different shortcut to follow instead. It fires regardless of what currently has focus (not just a global "no input focused" guard), since Ctrl/Cmd+K isn't a text-editing shortcut anything else in this app binds; pressing it again while already open closes it (`toggle()`, not just `open()`). **`isOpen`/`query` are plain in-memory state, not URL-synced** — a deliberate departure from the `?tab=`/`?range=`/`?view=` convention used everywhere else (Tasks/Calendar/Insights/Settings): those all represent "which mode of a persistent view am I looking at," worth bookmarking or sharing; a transient overlay with no per-item deep-linking need (unlike the task drawer's `?task=`, which exists specifically so a particular task can be linked to) has nothing worth putting in the URL, and every reference implementation (the four apps above) keeps this local too.

**Search scope: a live client-side filter over `useTasks()`/`useProjects()`'s existing reactive arrays** (task titles + project names, case-insensitive substring match), not a new indexed search structure — stated explicitly per the phase instruction, since a personal task app's dataset is small enough that scanning it on every keystroke is free, and building/maintaining a search index would solve a scale problem this app doesn't have. Notes/subtasks are deliberately not searched (task titles + project names only, matching "at minimum task titles... projects are cheap to include" from the brief) — broadening scope further is a future decision, not an oversight. Task results are **not** filtered by status — a completed task is still findable (useful for reopening/checking on it), unlike most list views which hide `done` by default.

**One unified, filterable list, not separate "search mode" vs. "browse mode" UIs.** `CommandPalette.vue` builds four possible sections — Tasks, Projects, Navigate, Actions — and filters all of them by the exact same query string. Tasks/Projects only ever appear once a query is actually typed (listing every task with an empty query would just be the whole task list, not a useful command surface); Navigate/Actions show their full set by default and narrow as you type, so typing "cal" surfaces the Calendar nav item the same way it would surface a task titled "Call the dentist." Navigate is built directly from `routes.ts` filtered to `showInSidebar` (reusing the same single source of truth `Sidebar.vue`/`BottomNav.vue` already read from — a route added there automatically appears in the palette with no separate list to maintain).

**Actions, exactly the two the brief called "at minimum," not more:** "New Task" (`openTaskDrawer()`, reused directly) and "Plan My Day." The latter reads `usePlanner().hasPlan` and **relabels to "View today's plan"** once today already has one, navigating there instead of re-invoking `generatePlan()` — `generatePlan()` is already a safe no-op on a planned day (Phase 8), but presenting a button still labeled "Plan My Day" that visibly does nothing when clicked would read as broken even though nothing is technically wrong; relabeling makes the palette's own state honest about what clicking it will do. A "New Project" action was considered and deliberately left out: `ProjectDialog` is mounted locally per-view (`ProjectsView`/`ProjectDetailView`), not globally like `TaskDrawer`, so a palette action would either need to globalize it (an architecture change out of scope here) or navigate-then-somehow-trigger-it (no existing mechanism for that). Worth revisiting only if `ProjectDialog` ever becomes global for an unrelated reason.

**Built on the existing `Dialog`/`DialogContent` primitives, not a new `cmdk`-style component family** — reused (not reinvented) the same way `ProjectDetailView`'s confirm dialogs and `PlanPanel`'s Regenerate confirm do, just reshaped via `DialogContent`'s existing `class` prop (`top-24 ... translate-y-0` overrides the default vertical-center position via `tailwind-merge`, same mechanism every other `class` override in this codebase already relies on). This is also most of the **accessibility groundwork for a global overlay done now, not deferred to Phase 14's app-wide pass**: reka-ui's `DialogContent` already provides focus trapping, `role="dialog"`/`aria-modal`, Escape-to-close, and focus return on close, for free — `CommandPalette.vue` only had to add a visually-hidden (`sr-only`) `DialogTitle`/`DialogDescription` pair (reka-ui warns in dev if a `DialogContent` lacks an accessible name/description) since the palette's visual design has no visible heading. **Keyboard interaction the palette itself owns** (not part of Dialog's built-in behavior): `ArrowUp`/`ArrowDown` move a `selectedIndex` through one flattened list spanning all visible sections (wrapping at both ends), `Enter` runs the selected item, both bound via `@keydown` on the search input — verified end-to-end keyboard-only (open via shortcut, type to filter, arrow to a result, Enter to execute) with zero mouse interaction anywhere in the flow.

**Two visible triggers, not one** — `Sidebar.vue` gets a "Search" button (with a ⌘K hint badge) next to "New Task"; `BottomNav.vue` gets a second small floating circle next to the existing New Task circle, rather than a 6th flex-1 item squeezed into the already-5-item nav row. The BottomNav trigger matters more than the Sidebar one in practice — there's no keyboard on a touch device, so it's the *only* way to reach the palette on mobile, not just a convenience alongside Ctrl/Cmd+K.

**Regression fixed post-Phase-14** (found via an actual screenshot at mobile widths, not code review): both floating circles were originally positioned with `top-0`/`top-1` + a `-translate-y-1/2`, i.e. centered ON the nav bar's top border — which means half of each circle's height always intrudes into the icon row underneath by construction. Centered horizontally on the whole 5-item bar, that intruding half landed squarely on the middle "Tasks" item, hiding its icon; the two circles' horizontal spans also overlapped each other by 8px. Fixed by anchoring both to `bottom-full` (the nav's own top edge) plus a margin instead, so they float entirely above the bar with no vertical intrusion at all, and widening the Search button's horizontal offset so there's a real gap between the two circles. Verified at 375/390/414px viewport widths.

### Routing

`src/router/routes.ts` is the single source of truth for navigation — each route's `meta` (`title`, `icon`, `showInSidebar`, `showInBottomNav`, typed via `route-meta.d.ts`) drives `Sidebar`/`BottomNav` (via `src/components/layout/navIcons.ts`, which maps the `icon` string to a `@lucide/vue` component) instead of a separate hand-maintained nav list — add a route, and nav chrome updates itself. All route components are lazy-loaded. `/settings` sections are tabs within one view, not nested routes.

**Task drawer / `?task=` query param.** The task creation/edit drawer (`src/components/task/TaskDrawer.vue`) is global UI state, not a route — it's mounted once from `AppShell.vue` and controlled entirely by `useTaskDrawer()`, whose `taskId`/`isOpen` are a `computed` derived from `route.query.task` (not a separate ref kept in sync by hand). This is why the browser back button and `Escape`/overlay-click all correctly close it: every close path — explicit `closeTaskDrawer()`, the Sheet's own `update:open` event, or a real back-navigation — ultimately just changes (or un-changes) `route.query.task`, and the same `computed` reacts regardless of which one triggered it. `openTaskDrawer(id?)` with no `id` calls `taskService.createDraftTask()` (empty title, `estimatedDuration: 0`, `createdViaDraft: true`) *before* navigating, so there's a real row with a real id by the time `?task=` is set — the drawer never renders a local-only "new task" state distinct from editing.

**Abandoned-draft cleanup.** `TaskDrawer.vue` has its own `watch(taskId, (_, oldId) => ...)` that fires on every task switch — including the drawer closing via *any* path, since a real back-navigation changes `route.query.task` directly without ever calling `closeTaskDrawer()`. If the closing task's local `createdViaDraft` ref is still `true` and its local `title` ref is still empty, it calls `deleteTask(oldId)`; a non-empty title (even if `createdViaDraft` is still technically `true`) is left untouched — nothing ever clears the flag. This deliberately reads the component's own local refs rather than re-fetching the task from Dexie: title saves are debounced ~400ms, so a fresh Dexie read at close time could still see a stale empty title for a task the user just named and immediately closed, and wrongly delete it. The debounced field saves (`saveTitle`/`saveNotes`/`saveDuration`/`saveDueDate`) correspondingly capture the target task id as an argument at the moment each keystroke schedules the save, not by reading `taskId.value` when the timer fires — otherwise closing within the debounce window would silently drop the save instead of just being a moot point for a deleted draft.

`Sidebar` is CSS-responsive (`hidden md:flex`) and self-contains its own collapse state (a local `ref`, not persisted yet); `BottomNav` is `md:hidden`. Both are rendered unconditionally from `AppShell.vue` — there's no JS-level `isMobile` branching, so don't add a `useBreakpoint`-style composable unless a future phase (e.g. the drawer choosing side="right" vs side="bottom") actually needs mobile detection in script, not just CSS.

**`?view=` query param.** `TasksView.vue`'s List/Kanban toggle follows the same "state lives in the URL" convention as the task drawer: `view` is a `computed` off `route.query.view` (`'kanban'` or anything else → `'list'`), switched via `router.replace` (not `push` — toggling the view repeatedly shouldn't pile up back-button history entries the way opening/closing the drawer intentionally does). The 4 filter selects (project/status/priority/due date) are deliberately *not* URL-synced — local `ref`s only — since only the view toggle needed to match an existing convention; don't assume filters are shareable/bookmarkable if you're extending this view. The Kanban board's drag-and-drop is native HTML5 (`draggable="true"` on `TaskCard`, `@dragover.prevent`/`@drop.prevent` on the column) — no drag library — and the drop handler calls `useTasks().setTaskStatus()`, same as the checkbox toggle, never a direct Dexie write.

`CalendarView.vue` reuses the `?view=month|agenda` convention (same `router.replace` reasoning as Tasks). It additionally URL-syncs the visible month as `?month=YYYY-MM` (omitted entirely when it equals the current month, so `/calendar` alone always means "this month") — a deliberate **exception** to the "filters stay local, only the view toggle is URL-synced" boundary Tasks established. Reasoning: which month you're looking at is unlike a filter dropdown — it's plausible someone wants to bookmark/share a specific month, and stepping through months is navigation where landing back on the previous month via the browser back button is the expected behavior (confirmed in Playwright: one `router.push` per month step, browser back correctly undoes it). Month steps use `router.push` (not `replace`), same as the task drawer, for that reason. Both Month and Agenda read the same `visibleMonth`/`tasksInMonth` computed, so there's exactly one date-range query to verify, and switching view tabs doesn't reset which month you're on.

### Styling

Tailwind CSS v4 via `@tailwindcss/vite` (CSS-first config, no `tailwind.config.ts`). All design tokens live in `src/styles/tailwind.css`: light/dark theme via `:root` / `.dark` CSS variables, a custom type scale (`text-page-title`, `text-section`, `text-body`, `text-secondary`, `text-caption` utilities mapping to 32/20/14/13/12px per the spec), a mixed radius scale (`--radius-sm/md/lg/xl`), and `--color-priority-{urgent,high,medium,low}` tokens for priority badges. ### shadcn-vue

`components.json` and `src/lib/utils.ts` (`cn()`) are configured. `src/components/ui/` currently has hand-written `button`, `label`, `input`, `textarea`, `badge`, `checkbox`, `tabs`, `select`, `dialog`, `sheet`, `progress` — each a folder with one `.vue` file per part plus an `index.ts` barrel (and a `cva()` variants export for `button`/`badge`/`sheet`), following the real shadcn-vue "new-york" source structure so a future CLI-generated component would drop in compatibly.

**`Input`/`Textarea` model typing gotcha:** `Input`'s `defineModel<string | number>()` is intentionally broad (matches shadcn's own primitive), which means `v-model` to a narrowly-typed local ref (e.g. `Ref<string>`) fails type-checking — Vue's `v-model` requires the emitted type to be assignable back into the ref, and `string | number` isn't assignable into `string` alone. `TaskDrawer.vue` works around this by typing those local refs as `string | number` and coercing only at the save boundary (`String(value)`/`Number(value)`), rather than fighting the primitive's type. `Textarea`'s model is plain `string`, so it doesn't have this issue.

`Checkbox` (reka-ui `CheckboxRoot`) and `Select` (`SelectRoot`) both use `modelValue`/`update:modelValue`, but their value types are broader still (`boolean | 'indeterminate' | null` for Checkbox; a generic `AcceptableValue` for Select) — for these, don't use `v-model` shorthand against a narrow local ref either; bind `:model-value` + `@update:model-value` explicitly with a handler that narrows/casts before assigning (see `onTodayChange`, `onProjectChange`, `onStatusChange` in `TaskDrawer.vue` for the pattern). Also note reka-ui's `Select` doesn't accept an empty string as an item `value` — `TaskDrawer.vue` uses a `'__none__'` sentinel for "no project"/"no priority" and translates it to `undefined` at the boundary.

The `shadcn-vue` CLI requires Node ≥22; this environment's Node is older (20.x when Phase 0/1 were built), so `npx shadcn-vue@latest init` / `add` fail with an `undici`/`webidl` crash — check `node -v` before assuming the CLI works. If it still fails when adding a new component, hand-write it against the existing files as templates (same reka-ui primitive names, same Tailwind token classes, same prop-delegation pattern: a `computed` that strips `class` out of `props` before `v-bind`-ing the rest, because declared props don't fall through automatically in Vue).

### Dates

`date-fns` is a dependency, but importing from its barrel (`import { format } from 'date-fns'`) fails type-checking under this project's TS version/`moduleResolution: "bundler"` combo — the package's `index.d.ts` re-exports via `export * from "./format.ts"` (a `.ts` extension that doesn't actually exist in the published package, only `format.d.ts`/`.js`/`.cjs` do), which this setup can't resolve. Import from the specific submodule instead: `import { format } from 'date-fns/format'`, `import { parseISO } from 'date-fns/parseISO'`, etc. — those resolve fine since the file names match directly.

**`src/utils/date.ts`** (`todayIso()`, `dateOffsetIso(days)`) is the one place `YYYY-MM-DD` "local today" strings should come from — use it instead of `new Date().toISOString().slice(0, 10)`. That inline pattern was used in a couple of places through Phase 5 (`useTasks()`'s `overdueTasks`, `TasksView.vue`'s due-date filter) and is subtly wrong: `toISOString()` is UTC-based, so near midnight in any timezone ahead of or behind UTC it can slice off the wrong calendar day relative to the user's actual local date. `date.ts`'s functions use the `Date` object's local getters (`getFullYear`/`getMonth`/`getDate`) instead, so they always match the user's own local day. Both prior call sites were refactored onto it when it was added (Phase 6) — if you find another raw `toISOString().slice(0, 10)` anywhere, that's a regression, not an intentional exception.

Phase 7 (Calendar) extended `date.ts` with month-level equivalents built the same way: `localIso(date)` (the underlying per-Date conversion, now exported so callers needing an arbitrary `Date` → local `YYYY-MM-DD`, like `CalendarView.vue`'s 42-cell month grid, don't reimplement it), `currentMonthIso()` (`YYYY-MM` for this month), `monthOffsetIso(monthIso, months)` (month navigation — negative steps back), `monthStartIso(monthIso)`/`monthEndIso(monthIso)` (feed directly into `useTasks().dueBetween()` for a month's task range, same pattern as Today's upcoming-deadlines window). Grid-specific concerns (which weekday a month starts on, padding in leading/trailing days to a fixed 42-cell/6-row grid) stay local to `CalendarView.vue`'s script — that's presentation, not a reusable date utility.

### PWA & polish (Phase 14)

`vite-plugin-pwa` is configured in `vite.config.ts` with `generateSW` (Workbox-generated service worker, auto-injected registration via `registerSW.js`) — there is no custom service worker file. `registerType: 'autoUpdate'` means a new SW installs and activates itself in the background with no user prompt, but **does not force-reload an already-open tab** — nothing in this app calls `virtual:pwa-register`'s update hook to trigger that (no update toast exists, and none was in scope for this phase). Verified precisely with a real rebuild-and-redeploy simulation, not just "the SW registered": using Playwright's `chromium.connectOverCDP` to keep one browser session alive across a stop-preview/edit-source/rebuild/restart-preview cycle (`vite preview` holds file handles on `dist/` that make rebuilding while it's running unreliable on Windows — stop it first), a reload *immediately after* a deploy still served the **old** bundle (the new SW was only `activating`), while the *next* reload after that served the **new** bundle — confirmed via an actual DOM attribute from the new code, not just a coincidentally-different filename. Offline behavior was verified with `context.setOffline(true)` (a genuine network cut, not stubbed routes): the precache (30 entries) serves the full app shell, and real IndexedDB data (a `today`-flagged task) rendered correctly on an offline reload.

**Icons** (`public/icons/`) were, at the time this phase shipped, a rasterized geometric placeholder (indigo square + off-white circle) — since superseded by real brand assets; see "Brand assets" below.

**Fonts** (`public/fonts/`) are now real: Inter Variable, fetched via `npm pack @fontsource-variable/inter` (the npm registry was reachable — confirmed via `npm ping` — even though this environment otherwise reads as offline-first-only) and re-hosted as two subset files — `inter-latin-wght-normal.woff2` (~48KB) and `inter-latin-ext-wght-normal.woff2` (~85KB), covering English plus most other Western/Central European accented characters. Deliberately excludes the cyrillic/greek/vietnamese subsets Fontsource also ships, since this app has no UI in those scripts; adding one later is just another `@font-face` block with the matching `unicode-range`, copied from the same package. License (SIL OFL 1.1, redistribution-permitted) is preserved at `public/fonts/LICENSE-Inter.txt`. Verified via `document.fonts` actually reporting `Inter ... loaded` and zero non-localhost network requests during load — confirming this is genuinely self-hosted, not silently falling back to a system font or hitting Google Fonts.

**Motion**: kept deliberately subtle per the spec's own "avoid distracting animations" wording, not a from-scratch animation system.
- **Page-to-page transitions** (previously missing entirely) — a 120ms cross-fade (`mode="out-in"`, in `AppShell.vue`) wrapping `RouterView`. `mode="out-in"` avoids the old and new page overlapping in normal document flow (which would otherwise need `position: absolute` during the transition to avoid a layout jump) at the cost of a *slightly* less instant feel — judged the right tradeoff for "subtle," not "fast at all costs."
- **Completion feedback** (previously an instant, un-transitioned strikethrough) — `transition-colors` added to `Checkbox.vue` itself (one fix point, covers every checkbox in the app — task rows, subtasks, the Plan panel) and to the 5 places a task/subtask title renders its done-state color change (`TaskListItem`, `TaskCard`, `TaskDrawer`'s subtask rows, `PlanPanel`'s two lists). `line-through` itself doesn't animate (not a meaningfully transitionable CSS property across browsers) — the color fading in while the strikethrough appears instantly is standard, unremarkable behavior other task apps use too, not a compromise.
- **Reduced motion was already fully handled before this phase — nothing new had to be built.** A global rule already existed in `tailwind.css`'s `@layer base` (`@media (prefers-reduced-motion: reduce) { *, *::before, *::after { transition-duration: 0.01ms !important; ... } }`, present since early phases) that collapses every CSS transition/animation app-wide, including `Dialog`'s `animate-in`/`zoom-in-95` (shared by every confirm dialog, `ProjectDialog`, and the command palette), `Sheet`'s slide transitions (`TaskDrawer`), and this phase's new page-fade and completion-color transitions — all for free, from one `*` selector. Verified with `page.emulateMedia({ reducedMotion: 'reduce' })`: `Sheet`'s computed `transition-duration` measured 0.3s normally and `0.00001s` under the media query, and the same held for the command palette's `Dialog` and the page-fade. **If a future animation is ever added via raw inline styles or a JS-driven animation library instead of a CSS `transition`/`animation` property, this global rule won't reach it** — that's the one way to accidentally regress reduced-motion support.

**Accessibility.**
- **Command palette** (Phase 13's two explicitly-deferred items, resolved here alongside the rest of the app's a11y work, not separately): the search input is `role="combobox"` with `aria-expanded`/`aria-controls`/`aria-activedescendant`; the results container is `role="listbox"`; each section is `role="group"` with an `aria-label` (the visible section heading itself is `aria-hidden`, since it'd otherwise be announced twice); each result is `role="option"` with `aria-selected` and `tabindex="-1"` (focus stays on the input the whole time — the standard accessible-combobox pattern — options are reachable by arrow key via `aria-activedescendant`, not by Tab). Verified `aria-activedescendant` actually changes on `ArrowDown`, not just that the attributes exist. The visual `kbd` hint row (↑↓/Enter/Esc) is `aria-hidden="true"` — a screen reader already gets equivalent-or-better instructions from the `role="combobox"`/`"listbox"` semantics and the (expanded) `DialogDescription`, so reading the hint row aloud too would just be redundant noise, not new information.
- **Custom toggle-button-groups** (plain `<button>` elements driving on/off visual state, found via grep for `aria-pressed`/`aria-selected`/`aria-checked` — there were zero uses anywhere before this phase) now carry real ARIA state: `AppearanceSettings.vue`'s System/Light/Dark buttons, `ProjectDialog.vue`'s color-swatch and icon-picker buttons, and `TaskDrawer.vue`'s specific-weekdays recurrence toggles all get `aria-pressed`. The weekday toggles also gained a proper `aria-label` (the full weekday name) separate from their single-letter visible glyph — "T" and "S" are ambiguous between Tuesday/Thursday and Saturday/Sunday non-visually, even though a sighted user disambiguates by position.
- **Icon-only buttons**: audited every `size="icon"` `Button` usage — all already had `aria-label` or an `sr-only` span (established convention since early phases); none were missing one.
- **Contrast — computed via the actual WCAG relative-luminance/contrast-ratio formula against the real token hex values (light and dark), not eyeballed.** Found two genuine failures, both fixed at the token level so the fix propagates everywhere the token is used, not patched per-component:
  - **`--input` (the `border-input` token used by `Input`/`Textarea`/`Select`'s trigger/`Button`'s outline variant) was identical to the purely-decorative `--border` token and only hit ~1.2–1.3:1 against the background** — far under the 3:1 WCAG 1.4.11 requires for identifying a UI component's boundary. Decoupled it to its own value in both themes (light: darkened; dark: lightened), now ≥3.05:1 against both `--background` and `--card` in both themes. `--border` itself was deliberately left untouched — card outlines and list dividers are decorative, not functional boundaries, so 1.4.11 doesn't apply to them, and changing it would have made the whole app's visual language noticeably heavier for no accessibility benefit.
  - **`PriorityBadge.vue` renders a priority color as both the text and a 15%-opacity tint of that *same* color as its background** — 3 of 4 priority colors failed 4.5:1 in at least one theme (light `high`/`medium` were structurally incapable of ever reaching 4.5:1 against any realistic tint, confirmed by checking their contrast ceiling against a pure white card — the text color itself was too light, not just the tint choice). Fixed by darkening (light theme) / lightening (dark theme) the specific failing `--priority-*` tokens just enough to clear 4.5:1 against their own actual composited badge background (not a plain white/black card), with a small margin above the exact threshold to absorb 8-bit hex rounding. Other usages of the same tokens (the Overdue banner's border/wash, plain-text labels) were checked too and are unaffected or improved, not broken, by the darker/lighter values.
  - **A genuine miss in this audit's first pass, found later via an actual screenshot, not the contrast formula: it never checked secondary/muted TEXT tokens as their own category** — it computed `--input`/`--border` (component boundaries) and `PriorityBadge`'s tokens, but nothing exercised `--muted-foreground` itself, and `--muted-foreground`'s hex value was never actually wrong (5.28:1 / 6.16:1 in light/dark — passes AA fine). The real bug was a **Tailwind v4 utility-namespace collision**: the type-scale token `--text-secondary` (13px, from `@theme`'s `--text-*` namespace) and the color token `--color-secondary` (from `--color-*`) both generate a class literally named `.text-secondary` — one sets `font-size`, the other sets `color: var(--secondary)` (a muted *background* tone, not intended as a text color anywhere in this app). The color rule won the cascade, so every element styled `text-secondary text-muted-foreground` (the date subtitle under Today's greeting, "Today's workload"/"Today's tasks", every Settings tab section heading, ~30 sites app-wide) silently rendered in `--secondary` instead of `--muted-foreground` — nearly invisible against `--background` in light mode. Fixed by renaming the type-scale token/utility to `text-meta` (no other `--text-*` scale step collides with a `--color-*` name). **Lesson for future contrast passes: audit text-color tokens as their own explicit checklist item, separate from borders/components — and remember a token's hex value being correct doesn't prove the utility class using it actually renders that color, if a namespace collision is silently overriding it.**

### Brand assets (post-Phase-14)

Real logo assets (two source renders, kept as-is in `src/assets/` as the master art) replaced the Phase-14 geometric placeholder: a square icon mark (indigo teardrop + a second, darker teardrop forming a stylized "S", on its own near-black rounded-square backplate) and a horizontal lockup (the same mark + a "Sora" wordmark). Both source renders are AI-generated raster art, not vector — there are no editable paths, only pixels, which shaped every decision below.

**The icon mark and the lockup intentionally use two different shades of near-black for the mark's second shape — this is deliberate, not an inconsistency to fix.** An earlier pass standardized the square icon's second shape (originally a muted blue-gray, `#444b57`) to match the lockup's near-black (`#101524`) exactly, reasoning that one color everywhere was more consistent. That recolor was reverted: it dropped the second shape's contrast against the icon's own near-black backplate (`#0c111c`) to ~1.04:1 — at small self-contained sizes (favicon, collapsed sidebar) the mark read as "an indigo shape on a dark tile," not a legible two-tone "S". The square icon mark and the lockup are never viewed side by side (one's a favicon/home-screen icon judged on its own at tiny sizes; the other's the in-app header wordmark, judged against the app's own light/dark surfaces) — so they don't need to share an exact hex value, and small-size legibility matters more here than cross-asset color matching. The icon's second shape is back to its original `#444b57` (**~2.15:1 against the backplate, roughly double the reverted value** — computed via the same WCAG formula as Phase 14's audit), and the lockup keeps its own near-black (`#101524`) unchanged.

**PWA icons** (`public/icons/icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `apple-touch-icon.png`) are all generated from the square icon mark (original colors, unrecolored), flattened to a true full-bleed square first (the source render has transparent rounded corners baked in — a solid rect in the backplate's own sampled color, `#0c111c`, was drawn behind the art before compositing, so the exported PNGs have flat square corners with no pre-baked rounding, avoiding double-rounding when the OS applies its own mask). No extra padding was needed for the maskable variant specifically — measured, not assumed: the mark's actual shape content (excluding the backplate fill) only spans ~55–59% of the canvas in each dimension, comfortably inside the ~80% maskable safe zone already, so `icon-maskable-512.png` reuses the exact same composited art as `icon-512.png` rather than a separately-padded version.

**`favicon.svg`** was replaced by embedding a 128×128 raster of the same flattened icon art as a base64 `data:` URI inside an `<image>` element — not a hand-traced vector, since the source art has no paths to trace, only pixels. Kept as `image/svg+xml` at the same path so `index.html` and `vite.config.ts`'s `includeAssets` needed no changes.

**The horizontal lockup** (`src/assets/logo-lockup-for-light-theme.png` / `-for-dark-theme.png`) replaces the plain-text "Sora" wordmark in `Sidebar.vue`'s header. Cropped tightly from the source render's alpha bounding box (transparent background, no backplate — unlike the PWA icon, a wordmark lockup shouldn't carry its own boxed background). **Two color variants, not one** — swapped purely via Tailwind's `dark:` variant (no new reactive state; `useTheme()` already toggles the `.dark` class this keys off of): the light-theme variant keeps the source's original near-black text/shape as-is (it was already correct, no recolor needed); the dark-theme variant recolors that same near-black family to `#ecebe8` (the app's own dark-theme `--foreground` token, for cohesion with the rest of the UI's dark-mode text) while leaving the indigo shape untouched in both — confirmed by direct rendering that indigo alone already reads fine against both a light and a dark sidebar surface. This is the *opposite* situation from the PWA icon: here the mark sits transparently against the app's real theme surface, not a fixed backplate, so a light/dark pair was actually necessary (and works well — verified in-browser at the lockup's real ~24px header height in both themes).

Collapsed-sidebar state (previously blank — the old plain-text wordmark had no collapsed equivalent) now shows a small `icons/icon-192.png` glyph instead. This reuses the *backplated* icon (self-contained, fixed colors) rather than a third lockup-style crop, specifically so it doesn't need its own light/dark variant — trading a bit of the low-contrast tradeoff noted above (visible at this small size too) for one fewer asset pair to maintain.

Reminders/notifications are foreground-only by design: there's no backend to push from, so `useReminderScheduler` fires browser `Notification`s via an in-page timer while the app is open/backgrounded, not via service-worker push. Don't add a push backend or `notificationclick` SW handler without an explicit decision to change this constraint.

## Product constraints worth knowing before implementing a feature

- The planner ("Plan My Day") **never silently reschedules** — it only writes a recommended `DailyPlan` on explicit user action and surfaces overflow tasks rather than auto-moving them. Implemented in Phase 8: `TodayView.vue`'s "Plan My Day" button is enabled and calls `usePlanner().generatePlan()`, which is a no-op once today already has a plan; the only thing that replaces an existing plan is the explicit, confirm-gated "Regenerate" control in `PlanPanel.vue` (see the Planning system section above for the full reasoning). `Sidebar`/`BottomNav` still don't reference it at all (only "New Task" is a global nav action; "Plan My Day" stays Today-page-scoped per the spec's module breakdown).
- Recurring tasks: a `RecurringRule` generates concrete `Task` + `RecurringInstance` rows ahead of time (rolling window); instances and completion history are never deleted when a rule is paused/ended, so history is preserved.
- Inbox membership (not explicit in the spec) is: a task with no `projectId`, no `dueDate`, and not `done`. Assigning a project/due-date, or completing the task, moves it out of Inbox automatically.
- Deleting a project **never deletes its tasks** — `projectService.deleteProject()` unlinks (`projectId → undefined`) every task in that project inside the same transaction as the delete, confirmed reachable end-to-end from `ProjectDetailView`'s Delete button (not just present in the service). A now-unlinked task that also has no due date and isn't done will reappear in Inbox as a natural consequence of the Inbox membership rule above, not special-cased delete logic.
